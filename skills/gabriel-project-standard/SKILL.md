# Padrão de projeto

Fonte da verdade: `Gabriel-OS/references/padrao-de-projeto.md` e `decisions/log.md`. Exemplos vivos e provados: Xlondz, Rakmma, Maison Éclat. Os modelos em `references/templates/` (`claude/` = `.claude/`, `github/` = `.github/`) vêm do Maison (Node/pnpm); adapte, não copie às cegas.

1. **Levante antes de mudar.** Stack, comandos reais de lint/typecheck/teste/build, serviços externos (que viram stub ou variável falsa), branch padrão, se existe `staging`, deploy atual, dono do repositório. Repo pessoal privado não aceita proteção de branch: peça a Gabriel para movê-lo para uma org da enterprise. Uma issue para a adoção; trabalhe numa branch.
2. **Instruções.** `AGENTS.md` com menos de 700 palavras a partir de `references/AGENTS.template.md`: o que é o projeto, fluxo em passos com os comandos reais, invariantes de domínio, autoridade, docs sob demanda. `CLAUDE.md` é só `@AGENTS.md`. Texto antigo inteiro vai para `docs/development/agent-reference.md`, sem perda. `ARCHITECTURE.md` a partir de `references/ARCHITECTURE.template.md`, conferido no código.
3. **Permissões.** `.claude/settings.json` do modelo: pode (dev, git de tarefa, `gh pr create/merge --squash`, `git worktree remove`), pergunta (produção, SSH, banco remoto, deploy manual), nunca (force, `reset --hard`, `rm -rf`, `--force` em worktree, `gh pr merge --admin`, segredos). Troque `__PROJECT__` e ajuste aos comandos do projeto.
4. **Núcleo rápido e nuvem.** `scripts/fast-check.sh` (o `bin/ci` do Akita: lint, typecheck, unitários, build, sem credencial), `scripts/cloud-setup.sh` (troque `__GIT_NAME__`/`__GIT_NOREPLY_EMAIL__` pela identidade noreply do dono), `scripts/ensure-node.sh` com `test-ensure-node.sh` (instala em `pinned-node/<versão>`; cada script põe `ensure-node.sh --bin` no início do PATH do próprio processo e nunca reaponta `~/.local/bin`, que projetos com versões diferentes disputariam; Source: my-skills#4), `scripts/ensure-pnpm.sh` com `test-cloud-setup.sh` (o pnpm fixado em `pinned-pnpm/<versão>`, instalado pelo npm do Node fixado num diretório temporário com troca atômica e `flock`; `cloud-setup` e `fast-check` põem os dois `--bin` no início do PATH do próprio processo e conferem com `--check`; nunca `npm install --prefix ~/.local`, cujo `bin` traria o `node` de outro projeto para a frente; Source: my-skills#12). Sessões de vários projetos dividem a máquina: `share-machine.sh` limita os workers do vitest fora do CI e põe build, workerd/e2e e prova D1 em fila (`heavy`, `flock` em `~/.cache/gabriel-heavy.lock`, espera com limite); o `fast-check` lista os 5 testes mais lentos. Teste unitário perto do timeout é defeito: fixture menor, mock ou suíte pesada, nunca timeout maior. Source: my-skills#5. Preencha `__DUMMY_ENV__` só com valores falsos e públicos. Prove num ambiente limpo (`env -i`, HOME vazio).
5. **Gates obrigatórios (não apague passos do CI):** `scripts/__PROJECT__-workflow.py` fornece `doctor` e `staging-ready --expected-sha <sha> [--promotion]` (passo 7); `scripts/check-pr-scope.py` exige branch `<tipo>/<N>-...`, `Refs #N` e exatamente uma nota `changes/<N>-<slug>.md` da própria issue, e recusa `CHANGELOG.md` e nota alheia; o PR de release é o que muda a versão do `package.json` e só apaga notas (todas). PR que toca `.github/**`, `scripts/**` ou `package.json` roda o próprio CI e gates (risco aceito por Gabriel): a descrição traz uma linha `Security-Review: <resumo>`. Sem eles o gate falha aberto. O `doctor` exige `docs/development/workflow.md`, `docs/development/skills.md` e `.codex/environments/environment.toml` com `.codex/scripts/setup.sh`: crie-os ou enxugue `DOCS` no script. Promoção por squash para a `main` também é promoção: só com OK de Gabriel. `__DUMMY_ENV__` vazio deixa o build ler `.env.local` real: preencha ou force no script.
6. **CI modo Akita.** `pr.yml`: check obrigatório barato no PR para `staging` (~1 min: segredos, escopo, versão, verificadores); o PR para `main` **não roda a suíte de novo**: só aceita origem `staging` do próprio repo, confere `staging-ready --expected-sha <sha> --promotion` e roda o audit estrito (a mesma suíte rodava 3 vezes por entrega, 23 a 55 min; decisão de 22/10/2026). O push na `main` só confere que a árvore é igual à da `staging` aprovada; se divergir, roda a suíte completa. Gatilho com `edited`; nenhum `if` no job obrigatório. `staging-quality.yml`: suíte pesada no push da `staging`, abre/fecha a issue "staging vermelha: <sha>". `dependency-audit.py` (padrão `--prod --audit-level moderate`) tira o veredito de `metadata.vulnerabilities` a partir do `--audit-level`, porque o pnpm 10 com `--json` sai 1 com qualquer advisory; `metadata` ausente ou não numérico é `failed`. Separa vulnerabilidade (vermelho) de fonte do audit indisponível (timeout, 5xx, rede): na staging, a indisponibilidade só abre a issue "audit indisponível: <sha>" (label `audit-indisponivel`) e a linha segue; só a promoção exige audit verde. Source: my-skills#7, #10, #11. Sem merge queue.
7. **Parar a linha.** O início de tarefa e o passo antes de cada merge rodam `staging-ready` sem `--promotion` na ponta da `staging`: só **vermelha** (pesada concluída sem sucesso no SHA exato, ou issue "staging vermelha" aberta) bloqueia; pesada `queued`/`in_progress` ou aviso "audit indisponível" **não** bloqueiam, senão os merges viram fila um a um. Só `--promotion` exige a pesada concluída e verde e o audit verde. Source: my-skills#13.
8. **Entrega.** Crie `staging` a partir da branch padrão. Rulesets via `gh api` (`references/rulesets.md`): `staging` e `main` só por PR, sem force nem deleção, check obrigatório do GitHub Actions, **sem strict nos dois**; `staging` só squash; `main` squash e merge commit. O merge da promoção (`--merge`) fica em "pergunta" no settings; o push de branch de tarefa não pede confirmação (asks estreitos `git push origin * *` e `git -C * * push *`, nunca `git push:*`, que anula o allow; push em `main`/`staging` é deny). Promoção só com OK de Gabriel no chat, merge commit com `--match-head-commit`, gate `--promotion` no SHA da `staging`, sem rerodar a suíte; rode `staging-ready --expected-sha <sha> --promotion` de novo logo antes do merge (o check verde do PR não expira quando a evidência muda). Versão cortada na promoção (`release.mjs` ou equivalente); PRs com `Refs #N`, nunca `Closes`. **Notas de mudança** (`references/templates/changes/README.md` vira `changes/README.md`): cada PR de tarefa cria uma nota `changes/<N>-<slug>.md` e não toca o `CHANGELOG.md`; `release.mjs check` valida nome e conteúdo (`- item`, continuação indentada, `### <categoria>` da lista do script) e exige `## Unreleased` vazio. O PR de release muda a versão: `release.mjs prepare --bump ...` junta as notas por categoria, em ordem de issue, e apaga os arquivos (PRs paralelos não conflitam). Na adoção, o `## Unreleased` com itens vai uma única vez para `changes/0-unreleased-legacy.md`. Implementação de referência: Maison #411. **Medida:** ao fim da promoção (deploy de produção concluído), rode `python3 scripts/delivery-time.py promotion --pr <N> --comment <issue>` e publique na issue de promoção o comentário que ele imprime; `delivery-time.py task --pr <N>` mede um PR de tarefa. Só lê (`gh api`); ajuste os nomes de workflow no bloco de configuração do topo. Source: my-skills#19.
9. **Revisor de domínio** (opcional, só se houver invariantes que um revisor genérico não conhece): `references/reviewer.template.md`, ~120 palavras, Claude `claude-opus-5-5`/`high` e Codex com modelo fixo. Sem "specialist".
